Submission format requirements (from official page)

  • Same CRS as training data: EPSG:32611 (UTM 11N)
  • Same resolution: 100m
  • Same bounds: 3292×3730, transform (100,0,243350,0,-100,4508550)
  • Single layer, float32, values between 0 and 1, higher = higher fault probability
  • Data outside bounds is null or NaN (but all-finite with zeros outside also accepted per reference solution and identical scores for NaN vs all-finite)

Verified: official submission format

Why “Predicted values must be in range [0,1]” happens and how we fixed it

Two mechanisms, both measured on competition's own data:

  1. Float32 sentinel -3.4e38: training_features.tif encodes nodata as -3.4028234663852886e+38. All 19 bands carry it on 3,061 pixels inside 5,167,373 footprint (band 6 tc: 3073). Left unsanitized, those ship values near -3.4e38 → outside [0,1].
  2. Valid mask smaller than template: Band 1 valid 5,165,852 vs template 5,167,373 → 3,061 scored pixels as NaN if mask from feature band.

Fix: footprint only from np.isfinite(sample_submission.tif), map NaN→0, +Inf→1, -Inf→0, clip to [0,1], write with nodata=None, re-read bytes and assert all 12,279,160 finite and in range.

Measurement record: GEMSDOE30 range-error root cause

What this file is and is not

  • Is: Unique candidate (38,888 dots, not 37,654 nor 44,090), all-finite, format-verified, built from power-law fault population + Poisson-disk + MT edge + gravity + ASTER corroboration
  • Is not: Organizer-scored. No score in this repo is organizer-verified. This is research candidate, not proven improvement. Only hidden new-fault labels can score it.
  • Unique vs registry: Distinct against all 23 historic group submissions (Jaccard <0.8 threshold). Most similar is GEMSDOE32 H33-2-B2 (Jaccard ~0.3 estimated, different count and physics).
